# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Zephyr RTOS firmware (nRF Connect SDK v3.2.4) for a custom IoT tracking tag based on the Nordic nRF52833 SoC (Arm Cortex-M4, 128 KB RAM, 512 KB Flash). The tag integrates Ultra-Wideband (DW3000 via SPI1), BLE NUS, NFC Tag Type 4 (T4T), a WS2812 RGB LED, a button, a LIS2HH12 accelerometer (I2C0) and an nPM1304 PMIC/charger (I2C0).

Board definition: `boards/Innovaforce/nRF52833_tag/`  
Application entry point: `src/main.c`

## Build & Flash

`west build -b nRF52833_tag` (board root is this repo). **The user builds and flashes the firmware themselves** and reports errors and BLE output back — do not assume a build or flash can be run here.

## Host Tests

There is no Zephyr test harness: `native_sim` / `unit_testing` are POSIX-arch boards and do **not** configure on Windows. Instead, the logic-only modules are split from their Zephyr glue (`*_core.c`, `cal_math.c`, `pos_residual.c`, `batt_curve.c`, `batt_window.c`, `tag_ui_color.c`, `uwb_net.c`, `uwb_frame_802_15_4z.c`) and compiled directly with a host gcc — one `main()` per test, `CHECK()` macro, non-zero exit on failure. There are no CMakeLists under `tests/`.

gcc is **not on PATH**; use WinLibs gcc (not clang), full path — see the header of any file in `plan/` for the exact location on this machine:

```bash
GCC="/c/Users/.../WinLibs.../mingw64/bin/gcc.exe"     # see plan/*.md for the full path
```

## Active Zephyr Configuration (prj.conf)

Key configs currently enabled:
- `CONFIG_BT=y`, `CONFIG_BT_PERIPHERAL=y`, `CONFIG_BT_NUS=y` — BLE peripheral + Nordic UART Service
- `CONFIG_NFC_T4T_NRFXLIB=y`, `CONFIG_NFC_NDEF=y`, `CONFIG_NFC_NDEF_MSG=y`, `CONFIG_NFC_NDEF_RECORD=y`, `CONFIG_NFC_NDEF_URI_REC=y`, `CONFIG_NFC_NDEF_URI_MSG=y`, `CONFIG_NFC_NDEF_PARSER=y` — NFC T4T + NDEF encode/parse
- `CONFIG_SENSOR=y`, `CONFIG_I2C=y`, `CONFIG_REGULATOR=y`, `CONFIG_LED=y` — nPM1304 PMIC: the regulator driver applies the BUCK/LDO rails at boot; `CONFIG_LED` is only for the PMIC's hardware "charging" LED mode
- `CONFIG_FLASH=y`, `CONFIG_FLASH_MAP=y`, `CONFIG_NVS=y` — `storage.c` (cal record, NFC name)
- `CONFIG_FPU=y`, **`CONFIG_FP_SOFTABI=y`**, `CONFIG_CMSIS_DSP=y`, `CONFIG_CMSIS_DSP_MATRIX=y` — trilateration. Soft-float **calling convention** is mandatory: the precompiled DW3000 driver is `-m4-sfp`, and `FP_HARDABI` breaks the link
- `CONFIG_WATCHDOG=y`, `CONFIG_TASK_WDT=y` — boot guard (`wdt.c`)
- `CONFIG_PM=y`, `CONFIG_PM_DEVICE=y`, `CONFIG_PM_DEVICE_RUNTIME=y` — Zephyr power management. `CONFIG_PM` alone never touches the peripherals: without `PM_DEVICE` the `pinctrl-1 = <&..._sleep>` states already in the board DTS are dead text and SPIM3/TWIM0 stay clocked forever. `PM_DEVICE_RUNTIME` is what makes the nrfx SPIM/TWIM drivers suspend between transfers — they already call `pm_device_runtime_get/put` around every transaction; `zephyr,pm-device-runtime-auto` on `&spi3` and `&i2c0` in the board DTS is what arms it. **`&spi1` deliberately does not get the property** — the DW3000 path is driven from the GPIO ISR via `dwt_isr()` and suspend/resume is not safe there; `pm_device_runtime_get()` is a no-op on a device that never had runtime PM enabled, so omitting the property leaves SPI1 exactly as it was
- Board defconfig adds: `CONFIG_LED_STRIP=y`, `CONFIG_WS2812_STRIP_SPI=y`, `CONFIG_SPI=y`, `CONFIG_ARM_MPU=y`, `CONFIG_HW_STACK_PROTECTION=y`, and the console/log disables

Board-level defaults live in `boards/Innovaforce/nRF52833_tag/nRF52833_tag_defconfig`.  
To enable a new subsystem, add the `CONFIG_*` line to `prj.conf`.

## Application Behavior (main.c)

Full UWB ranging + dynamic anchor selection system. Boot does **not** block on a BLE connection (`ble_log_wait_ready()` exists but is no longer called from `main`), so early diagnostics are sent into the void — read state back with `cal status` / `pwr ...` after connecting.

1. LED strip device check; hang on failure.
2. `ble_log_init()` — starts BLE advertising; `ble_log_set_state_cb(batt_on_ble_state)` gates the idle-current window.
3. `storage_init()` — NVS mount (`STOR fail` on error).
4. `tag_wdt_start_boot_guard()` — arms the 10 s watchdog **before** DW3000 bring-up, so a hung init resets and retries the boot.
5. `uwb_init(3)` — three retries; `probe fail N/3` / `init fail N/3` per failure, `all 3 fail` on total failure. On success `main` sends `Config OK`.
6. On failure: LED **red** (the only signal available with no BLE), `DW3000: init failed\n`, hang. The watchdog is never fed, so the SoC resets in ~10 s.
7. `cal_init()` — `CAL loaded` or `CAL REQUIRED`.
8. `nfc_tag_init()`, `tag_cmd_init()`, `rx_stats_reset()`.
9. `uwb_ss_initiator_start()` + `uwb_net_runner_start(eui)` — EUI is derived from `NRF_FICR->DEVICEID`. BLE NUS output is `P:x.xx,y.yy\n` once per superframe when ≥3 anchors are visible and calibration is loaded.
10. `motion_init()`, `tag_ui_init()`, `batt_monitor_start()`, then `tag_wdt_run_feeder()` — from here the watchdog is fed forever.

The RGB LED is **dark in normal operation**; it lights only for the button readout (`tag_ui.c`) or the fatal-init red.

## Key Patterns

- **BLE NUS transmit:** `ble_log_init()` → `ble_log_send(msg)`. Sends before a central subscribes are simply dropped; `ble_log_wait_ready()` blocks on a semaphore until notifications are enabled, but `main.c` deliberately does not call it (boot must not depend on a phone being present). `ble_log_send` retries internally on `-ENOMEM` (TX buffer momentarily exhausted by back-to-back sends). NUS is the *only* debug channel, and it also costs power — see the BLE-idle-window caveat under the battery pattern.
- **BLE advertising is event-driven, not continuous — press the button before you expect to connect.** `BT_LE_ADV_CONN_FAST_2` running forever cost ~150 µA, roughly 60 % of the whole 250 µA power target, for a channel nothing operational depends on (positions reach the gateway over the `0xEA` POS frame). `ble_log_init()` now starts **no** advertising at all. `ble_log_adv_window()` opens a 60 s connectable window at `BT_GAP_ADV_SLOW_INT_MIN/MAX` (1–1.2 s, ~20 µA) and is called from the button **single press** (the same gesture that shows the battery colour) and from the NFC field-on / NDEF-write callback. It is idempotent — a second call restarts the 60 s timer — and safe from any thread including the BT RX thread, because it only submits to the system workqueue (`bt_le_adv_start()` from the BT RX thread deadlocks; see `adv_work_fn`). Advertising runs **continuously** while `pwr adv on` is set or while `uwb_radio_sleep_enabled() == false` (`pwr sleep off`), so bench debugging is unaffected. On disconnect a fresh 60 s window opens rather than advertising forever. **Consequence: anything only reachable through a NUS string — `cal status`, `cal last`, `rst`, `fault`, `stack`, `pwr idle`, `pwr rx`, `pwr sched`, `pwr scan` — needs a button press first.** A freshly flashed tag is not discoverable until it is touched.
- **BLE NUS receive / commands:** exactly one RX handler slot (`ble_log_set_rx_handler`), owned by `tag_cmd.c`. `tag_cmd_on_rx` truncates to 24 bytes, strips CR/LF, handles `pwr sleep on|off`, `pwr idle`, `pwr rx`, `pwr rxrst`, `pwr adv on|off`, `pwr tier` (bare = the three rows as they will actually be used, i.e. after `UWB_LISTEN_SKIP_CAP`; `pwr tier f|s|i <skip> <every>` sets one; `pwr tier def` restores the compiled defaults), `pwr sched` / `pwr schedrst` (beacon-scheduler period estimate, planned window, effective skip, consecutive misses, and lifetime ok/miss counts), `pwr scan` (coverage-ladder rung + probe interval in seconds), and forwards everything else to `cal_on_rx` (`cal <mm>`, `cal status`, `cal clear`, `cal selftest`). New commands go here, not into a second handler. The callback runs on the BT RX thread.
- **NUS 20-byte payload limit:** Default ATT MTU is 23, so a single notification carries at most 20 bytes. `bt_nus_send` does not auto-fragment — payloads >20 bytes fail with `-EMSGSIZE` and are silently dropped. Keep diagnostic strings short (e.g. `"probe fail 1/3\n"`, `"ID=0xDEADBEEF\n"`), or initiate an MTU exchange before transmitting long messages. **This limit bites twice and silently**: `twr_log()` first truncates to `TWR_MSG_LEN`=20 via `vsnprintf`, then NUS drops anything still over 20. A 50-char diagnostic line in the cal path was cut to 19 chars for months, hiding every counter it printed after the second field — split long diagnostics into several short lines and count the bytes rather than assuming.
- **Linking the precompiled Decawave driver:** `libdwt_uwb_driver-*.a` registers per-chip drivers (DW3000/DW3700/DW3720) into the `.dw_drivers` linker section via static objects. Nothing in app code references those symbols, so the linker would skip the .o files. `zephyr_ld_options(-Wl,--undefined=dw3000_driver)` in `CMakeLists.txt` forces `dw3000_device.c.obj` into the link, populating the section so `dwt_probe()` can find a matching driver. Do **not** use `-Wl,--whole-archive` — CMake 3.21 (nCS 3.2.4) strips the matching `--no-whole-archive` as a duplicate and the flag leaks into picolibc/libgcc, causing multiple-definition errors on `calloc`/`free`/`malloc`/`__retarget_lock_*`/etc.
- **GPIO interrupts:** Use `gpio_pin_interrupt_configure_dt()` with `GPIO_INT_EDGE_BOTH`; never use the button subsystem — GPIO is managed manually to avoid conflicts with the NUS setup.
- **SPI rate switching:** Call `openspi()` / `closespi()` in `deca_spi.c` when changing between init (4 MHz) and fast (32 MHz) modes; the static RX buffer is required for EasyDMA.
- **DW3000 critical sections:** Always bracket Decawave library calls that touch the IRQ with `decamutexon()` / `decamutexoff()`.
- **`CONFIG_ASSERT=y` is incompatible with this firmware's ranging** — it belongs in `debug.conf` only. `k_mutex_lock()` and `spi_transceive()` both carry an unconditional `__ASSERT(!arch_is_in_isr(), ...)` placed *above* their non-blocking fast paths, and `dwt_isr()` reaches the DW3000 through both. So with asserts on, every DW3000 interrupt panics the kernel (`K_ERR_KERNEL_PANIC`, `LR` → `kernel/mutex.c`). It is invaluable for diagnosing other classes of bug — it is how the calibration crash was closed out — but a build with it on cannot range.
- **`dwt_isr()` runs in the GPIO ISR, and blocks there — known, deliberate, do not "fix" it blindly.** Every DW3000 register access goes through `readfromspi()`/`writetospi()` (`platform/deca_spi.c`), which take `spi_mutex` with `K_FOREVER` and then block inside `spi_transceive()` on a completion semaphore. Blocking in an ISR is illegal in Zephyr: an uncontended `k_mutex_lock()` takes a fast path and works, but a contended one would call `z_pend_curr()` and suspend whatever thread the interrupt preempted. **This is a real latent bug and it is still present.** It was *not*, however, the cause of the calibration crash (that was an array overrun — see Open Work), and the obvious fix makes things worse: deferring `dwt_isr()` to thread context via an ISR notifier + semaphore was implemented and **reverted**, because it cut accepted ranges from 100 to **1 per calibration iteration** (`CALp 100 1` with zero size/header rejects — 99 pure RX timeouts). Ranging depends on the handler running promptly inside the ISR and draining the device in one pass; a semaphore hand-off does not preserve that. **The correct fix is to make the SPI path ISR-safe** (a polled, no-wait transfer when `k_is_in_isr()`), not to move `dwt_isr()`. `process_deca_irq()` is iteration-capped at 16, because its loop condition is "the DW3000 still asserts IRQ" and an enabled-but-uncleared status bit would otherwise spin forever *inside an interrupt*.
- **Adding a peripheral to I2C0:** Add the node under `&i2c0` in `nRF52833_tag.dts`; the bus is already enabled with the correct pins.
- **Battery via the nPM1304 (there is no fuel gauge):** the BQ274xx is gone. The PMIC's charger block (`npm1304_charger`, `<zephyr/drivers/sensor/npm13xx_charger.h>`) exposes the **sensor API**: `sensor_sample_fetch(fg)` then `SENSOR_CHAN_GAUGE_VOLTAGE` (mV = `val1 * 1000 + val2 / 1000`) and `SENSOR_CHAN_GAUGE_AVG_CURRENT` (`val1` A + `val2` µA). There is **no SoC channel** — `batt_read_soc()` maps the resting voltage through `lipo_mv_to_pct()`, which is ±10 pp in the 3700–3850 mV plateau; treat it as an estimate, not a gauge. While VBUS is present (`SENSOR_ATTR_NPM13XX_CHARGER_VBUS_PRESENT`, no fetch needed) the terminal voltage is charger-driven, so `batt_read_soc()` returns `-EBUSY` and `batt_soc_cached()` reports `0xFF` rather than a lie — `0xFF` is also the POS-frame `UWB_FRAME_POS_SOC_UNKNOWN` sentinel, and the two definitions must be changed together. `charging-enable` in the DTS is what actually switches the charger on; without it the battery current reads 0 mA on VBUS. `thermistor-ohms = <0>` disables the NTC because the pad is not on the PCB — a hardware constraint, not a missing setting. A **60 s** timer → workqueue samples SoC and, **only while BLE is disconnected**, accumulates current into the idle window (it was 5 s, which woke the MCU twelve times a minute for an I²C transaction to read a quantity that moves over hours; the window accumulates per *sample*, not per second, so its min/mean/max are unchanged and only the reported `n` gets smaller) (a live connection adds the BLE radio's draw and would skew the field estimate); read it with `pwr idle` after reconnecting.
- **Motion → ranging cadence:** `motion.c` programs the LIS2HH12 activity engine (FS 2g, **10 Hz**, `ACT_THS`=8 ≈ 125 mg, **`ACT_DUR`=6 ≈ 4.8 s**) and routes `int1_inact` to P0.28. **`ACT_DUR` is tied to the ODR and must move with it: its LSB is `8 / ODR` seconds.** At 50 Hz the LSB was 0.16 s and 31 gave ~5.0 s; at 10 Hz the LSB is 0.80 s, so the same window needs 6. Dropping the ODR (~180 µA → ~50 µA) while leaving `ACT_DUR` at 31 silently stretches the inactivity window to ~24.8 s — the tag keeps ranging at the FAST cadence for 25 s after it stops moving, which is the opposite of the intent and costs more than the ODR change saves. `ACT_THS` is unaffected (LSB = FS/128, ODR-independent). INT1 is an *inactivity* status with active-high polarity, so the pin is **HIGH while still, LOW while moving** — `ACCEL_INT_MOVING_LEVEL` is 0 (hardware-verified; flip it if the cadence inverts). The GPIO handler calls `uwb_set_moving()` → `uwb_net_set_moving()` (the **raw** state — `uwb_net_tier_filter()` in `uwb_net.c` owns the FAST/SLOW/IDLE hysteresis now, and it needs the edge rather than a conclusion drawn from it) plus `uwb_net_runner_wake()` so a motion edge does not wait out a multi-second skip. The pin is also sampled at init so the tier is right before the first edge. The accelerometer has no DTS node; `lis2hh12_if.c` binds ST's register-map driver to `i2c0` by hand at address 0x1E.
- **Button UI:** `tag_ui.c` runs its own thread; the ISR debounces (30 ms) and pushes **both** press and release edges (`struct btn_ev {t_ms, pressed}`) into an 8-slot msgq. Two presses within `DOUBLE_MS` (350 ms) = double press → `tag_alert_raise()`; held with no release for `LONG_MS` (3000 ms) = long press → `tag_alert_cancel()`, firing at the 3 s mark while still held (not on release), so a bounded wait on the queue is used rather than blocking for the release edge; otherwise single press → `ble_log_adv_window()` (the 60 s advertising window — this is the *only* routine way to make the tag discoverable) plus battery colour on the LED and `BATT:`/`I:` over NUS for 5 s. Gestures are decided from the timestamps, not from arrival order, because the thread can be descheduled while presses queue — multi-edge queuing (since Task 8 of the alert work) makes this more true, not less, since a release can now also be sitting in the queue mid-gesture. Releases seen while a gesture is being resolved are consumed, never mistaken for a fresh press.
- **Watchdog:** `wdt.c` uses Zephyr `task_wdt` with a 10 s timeout, armed *before* DW3000 bring-up and fed only after a successful boot (feeder thread, 3.3 s period). The nRF52833 WDT **cannot be stopped once started**, so any new long blocking operation on the feeder's path must stay well under 10 s or arm its own channel.
- **NVS access:** all persistence goes through `storage.c` (`storage_read/write/delete(id, ...)`) over the DTS `storage_partition`; ids in use are 1 (cal record), 2 (NFC name), and 3 (alert epoch/active, `src/tag_alert.c`). Do not open a second NVS instance.
- **NFC T4T:** `nfc_tag_init()` emulates a T4T tag holding a **text record with the tag name** (not the old URI), hand-encoded in `encode_name()` — NLEN (big-endian) + `0xD1 0x01 <len> 'T' 0x02 'e' 'n' <name>`, name ≤32 chars so the short-record form always fits. A phone write parses the incoming NDEF, updates the name and persists it to NVS. The `NFC_T4T_EVENT_NDEF_UPDATED` callback runs in the nrfxlib NFC thread (not ISR) — `ble_log_send()` is safe from it. The NFCT node must be enabled in the board DTS (`&nfct { status = "okay"; }`) for `HAS_HW_NRF_NFCT`, which `NFC_PLATFORM` and `NRFX_NFCT` need to build.
- **Dynamic anchor selection:** `uwb_net_runner.c` maintains an anchor pool (up to 6 entries) with EMA-filtered CIR quality scores. `run_discovery()` broadcasts an E2 frame and collects E4 DISCOVERY_RESPONSE frames within a `DISCOVERY_WINDOW_MS` window; `anchor_pool_rebuild_selected()` picks the top 3–4 anchors by EMA score into `selected[]`. `anchor_sweep()` ranges only those anchors via SS-TWR. Re-discovery runs every 10 superframes or when fewer than 3 anchors respond. `last_sweep_n` must be primed to the discovery count after the first discovery so the sweep gate (`last_sweep_n < ANCHOR_SELECT_MIN`) does not immediately re-trigger discovery.
- **Discovery window sizing:** The anchor firmware delays its E4 response by `DISC_BASE_UUS + anchor_id × DISC_SLOT_UUS` (currently 2000 + id × 3500 µs). `DISCOVERY_WINDOW_MS` in `uwb_net_runner.c` must exceed the highest anchor's slot: for anchor IDs 0–3 the maximum is 12.5 ms, so `DISCOVERY_WINDOW_MS = 15`. Formula: `ceil((DISC_BASE_UUS + max_id × DISC_SLOT_UUS) / 1000 + 2_ms_margin)`. If anchors with higher IDs are added, increase this constant.
- **`run_discovery()`'s RX loop must not slice its collection window into a fixed timer.** It used to re-arm the DW3000 receiver every `DISCOVERY_RX_SLOT_MS` (3 ms) regardless of whether a frame had arrived, and each re-arm (`dwt_setrxtimeout`/`setpreambledetecttimeout`/`setinterrupt`/`rxenable`) takes nonzero time — a real gap where the receiver isn't listening. Anchor id 2 (short address `0x0003`) replies at exactly `DISC_BASE_UUS + 2×DISC_SLOT_UUS = 9.0 ms`, landing precisely on a 3 ms slice boundary (3, 6, 9, 12, 15), so its response was the one structurally at risk every single discovery round — reproduced on the bench as "anchor `0x3` never answers `E4`, every cycle, once `pwr tier f 1 1` puts the runner at full speed." Anchor ids 0 (2.0 ms) and 3 (12.5 ms) fall safely inside a slice, which is why it was always specifically the middle anchor and never looked like an RF or hardware fault. Fixed by arming for the full remaining window each iteration (matching the beacon RX loop a few hundred lines below, which already re-arms only after actually consuming a frame) instead of capping every call at a fixed slice. If discovery ever again reliably misses one specific anchor while the others are fine, check first whether that anchor's `DISC_BASE_UUS + id×DISC_SLOT_UUS` delay lines up with some other fixed polling interval introduced since — that alignment, not the anchor, is the usual suspect.
- **BLE message queue budget:** `ss_twr_msgq` has 8 slots (K_NO_WAIT — overflow is silent). A full sweep of 4 anchors produces at most 4 ranging messages + 1 position = 5 slots; stay well under 8. Do not add per-anchor diagnostic lines during sweep — they consume slots and can starve the `P:` position output.
- **Position output:** `position_publish(pos, n_anchors, src_addr)` in `uwb_ss_initiator.c` formats and enqueues `P:x.xx,y.yy\n` via `twr_log()`, and also transmits a `0xEA` POS frame to the gateway (`uwb_frame_pos_build()`), carrying `pos->residual_m` and `batt_soc_cached()`. It takes no `uwb_radio_owner` claim: it runs inside the runner's own sweep, which already owns the radio, and would be claiming from itself otherwise. Called from `uwb_net_runner.c` after a successful `pos_solve()`. Output appears only when ≥3 anchors respond and calibration is loaded. `pos_solve()` uses CMSIS-DSP `arm_mat_inverse_f32`; returns false on singular matrix (anchors collinear or sharing coordinates).
- **HELP/CANCEL alert (`0xEB`, tag side implemented):** A double press (`tag_ui.c`) calls `tag_alert_raise()`; a long press ≥3 s calls `tag_alert_cancel()`. `tag_alert.c` (NVS id 3, `k_mutex`-guarded) wraps the pure `tag_alert_core.c` state machine — epoch increments only on a genuine new HELP, survives a reset (resumed, not re-raised, so the epoch does not advance across a reboot mid-emergency), and CANCEL keeps the epoch it is cancelling. `uwb_net.c` emits a new `UWB_ACT_SEND_ALERT` from **every** state including `UWB_ST_SCAN` (an unjoined tag is exactly the "no anchor in range" case the feature exists for) and it is deliberately **outside** `UWB_ACT_RANGING_MASK` — an uncalibrated tag must still be able to call for help. Emission rule (`alert_action()` in `uwb_net.c`): in `JOINING`/`DISCOVER`/`RANGING` it fires only on an actual `UWB_EV_BEACON`, never on a miss, because without the beacon the tag does not know where the CAP is; in `SCAN` it fires on both `UWB_EV_BEACON` and `UWB_EV_BEACON_MISS`, since an unjoined tag has no sync to protect and no seat to lose. **Transmit-from-runner rule (same as `position_publish()`):** the frame is built and sent from inside `runner_fn` in `uwb_net_runner.c`, in its own CFP slot or a CAP mini-slot, with **no `uwb_radio_owner` claim** — the runner already owns the radio there — and **no new `wait_event()` caller**; any future radio consumer must go through the existing handover, not add a third one. The execute block sits after JOIN/KEEPALIVE and before `UWB_ACT_RUN_SWEEP`/`UWB_ACT_SLEEP` in `runner_fn`, since the action word is a bitmask evaluated top to bottom and position in the function *is* the priority — an alert must not delay the sweep's slot-start deadline, and must not lose a whole superframe waiting behind `UWB_ACT_SLEEP`. `alert_relay.c` (dedup cache, gradient relay decision, gateway latch FSM) is compiled here too but is currently dead code on the tag — it exists so the anchor/gateway firmware can share the exact same epoch-ordering and dedup logic rather than reimplementing it (see `spec/2026-08-16-uwb-help-alert-design.md` §3/§6). **Anchor/gateway firmware is not implemented in this repo** — see Open Work item 5.
- **Anchor coordinates:** Each anchor stores `anchor_x`, `anchor_y`, `anchor_z` in flash (address `0x1E000`, `flash_record_t` with magic + CRC). Set via anchor console: `set anchor_x <float>`, `set anchor_y <float>`, then `save`. Values are written into E1 ranging response bytes 19–22 (X) and 23–26 (Y) as IEEE 754 float32 LE. Anchors must be non-collinear — if any two share (0,0) or all three are on the same line, `pos_solve` returns false.
- **Multi-tag (validated):** Multiple tags operating simultaneously is implemented and hardware-validated (tested up to 3 tags). Each tag JOINs the gateway, is GRANTed a distinct CFP slot, and ranges **only within its slot** — the TDMA time separation solves RX cross-contamination during ranging by construction (no per-tag frame filtering needed). Two fixes were required: **(1) beacon re-arm loop** (`runner_fn` step 2): `uwb_radio_rx_beacon()` returns on the first frame of ANY type, so with multiple tags another tag's poll/response/keepalive was misread as a beacon miss and `MISS_MAX` in a row bounced the tag to SCAN (`RESCAN miss`). The runner now re-arms RX, discarding non-beacon frames, until the real beacon arrives or the superframe budget elapses. **(2) slot sizing**: `T_SLOT_MS` must be ≥ the measured worst-case sweep (~22 ms 4-anchor, air-time bound at PLEN-1024/850k), so `T_SLOT_MS=24`; the original 15 ms let adjacent 16 ms-spaced slots overlap, causing inter-tag collisions (`n=3`). DISCOVERY (E2/E4) did **not** collide in practice with 3 tags (`DISC n=4` observed consistently), so the previously-feared discovery TX stagger was not the blocker; it may still matter at higher tag counts. **Real capacity ≈ 7 tags** (CFP budget ~180 ms / 25 ms slot spacing), below the protocol hard cap of 11 (`UWB_FRAME_N_CFP` / beacon slot-map). Capacity levers without sacrificing range: PLEN-512 @850k (~9 tags, −3 dB), 3-anchor sweep (~10, no redundancy), or both (~12). The `RESCAN seat`/`RESCAN miss` BLE log is permanent lost-sync telemetry.
- **Power saving — RX duty-cycle (hardware-validated):** Two layers cut consumption from ~66 mA to **~22 mA** (≈64 %). **Layer 1** deep-sleeps the DW3000 (`dw_enter_sleep()`/`dw_wake()` in `uwb_net_runner.c`, gated by `dw_sleep_enabled`, toggled with `pwr sleep on|off`) between activities in SLOW/IDLE tiers (~66→56 mA). **Layer 2 — narrow beacon window** (`beacon_track_core.c`): the open-ended beacon listen kept the receiver on ~91 % of every superframe (`RXon 182/190 ms`, measured via the `pwr rx` instrumentation). The runner now predicts the next beacon from an EMA of the gateway period (~195 ms in the tag's clock, **not** 200 ms — predicting from 200 ms accumulates ~5 ms/superframe of error) and, once `WARMUP_N` clean beacons confirm lock (ACQUIRING→TRACKING), sleeps the radio until just before the prediction and arms only a `±BT_GUARD_MS` (5 ms) window. A miss forces one full-window frame to re-acquire (so a single false miss can never trip `UWB_NET_MISS_MAX`=3 → RESCAN). Result: `RXon` mean ~30 ms (warmup-dominated; the narrow frames themselves are ~5 ms), arrival jitter only ~±0.12 ms once tracking (the tight window also de-jitters the software timestamp path). **Timing is in ms** (`uwb_radio_now_ms()`/`k_uptime`), not k_cycle — the DW3000's hardware timestamp clock stops in SLEEP, so hardware delayed-RX is incompatible with Layer 1; software timing composes cleanly. Tuning constants in `uwb_net_runner.c`: `BT_GUARD_MS`, `BT_WARMUP_N` (8; lowering toward 2 cuts the post-miss warmup penalty since `period_est` is retained across a miss), `BT_EMA_SHIFT`. **Diagnostics:** `pwr rx` reports `RXon mean/max ms`, folded arrival offset min/max µs, and beacon/miss counts; `pwr rxrst` resets the accumulator (use it after the tag locks to measure steady-state only — JOIN/re-discovery skips otherwise inflate the offset). Specs/plans: `spec/2026-06-23-rx-stats-*`, `spec/2026-06-24-narrow-beacon-window-*`, `plan/2026-06-24-narrow-beacon-window.md`. Host tests: `tests/rx_stats/`, `tests/beacon_track/`.
- **Power saving — Layer 3, superframe skipping (implemented, NOT yet measured on hardware).** Layers 1 and 2 above bottom out around 1 mA: a *perfect* 3 ms narrow window every 200 ms is still `3/200 × 66 mA = 990 µA`, four times the 250 µA target, before the MCU, BLE or the accelerometer. Maintaining 200 ms sync continuously is not affordable at any window size, so the tag must **skip whole superframes**. See `spec/2026-08-16-low-power-duty-cycle-design.md` and `plan/2026-08-16-low-power-duty-cycle.md`.
  - **Two cadences that used to be one.** `tier_cadence()` gated `UWB_ACT_RUN_SWEEP` *only*, so the tier setting never touched the dominant costs (beacon RX + `dw_wake()`, paid every superframe regardless of tier). It is replaced by a per-tier `struct uwb_tier_params { listen_skip, range_every }` in `uwb_net.c`: `listen_skip` is superframes slept between beacon re-syncs (where the power is), `range_every` is participations between fixes (where the update rate is). Defaults FAST {25,1}, SLOW {75,1}, IDLE {300,1}; settable at runtime with `pwr tier`.
  - **`UWB_LISTEN_SKIP_CAP` = 25, applied on *read*.** `UWB_NET_LEASE_SF` is 50 superframes and the gateway ages every lease once per superframe whether or not the tag was listening, so a tag sleeping longer than 25 superframes cannot renew. **FAST works against today's gateway; SLOW and IDLE do not.** Lifting the cap is a one-line edit and is gated on the gateway implementing design §7 (the tag declares its skip; the gateway sizes the lease as `max(LEASE_SF, 3 × declared_skip)`; the slot map keeps a sleeping tag's seat). Clamping on read, not on write, is what makes that a one-line edit.
  - **The lease must age by *elapsed* superframes.** `lease_age()` in `uwb_net.c` subtracts `ev->frame_counter - c->frame_counter`, not 1. Decrementing by one per *received* beacon was correct only while the tag participated in every superframe; at `listen_skip = 25` it would renew 25× too late and the tag would lose its seat on the very first skip (visible only as `RESCAN seat`). Pinned by `tests/uwb_net/test_lease_ages_by_elapsed()`.
  - **`beacon_sched_core` and `beacon_track_core` are complementary, not alternatives. Do not merge them.** `beacon_track` runs the ACQUIRING→TRACKING lock on full-window listens; `beacon_sched` then owns the prediction and may skip. The window a skip needs is dominated by the *period-estimate error × skip factor*, and an EMA over consecutive arrivals bottoms out at ~the arrival jitter. A two-point estimate over a baseline of `n` superframes, `P = (t_last − t0)/(fc_last − fc0)`, has error `jitter/n` instead — that 1/n scaling is the whole reason the module exists. The gateway's `frame_counter` supplies the denominator, which is also what makes a long skip self-correcting: every wake validates the estimate against ground truth. Q16.16 fixed point throughout (`CONFIG_FP_SOFTABI`, and this runs per superframe).
  - **`beacon_track` is deliberately not fed across a skip** (`if (eff_skip <= 1)` in `runner_fn`). Its EMA assumes *consecutive* superframes; one skipped window would push its period estimate to thousands of milliseconds. Once `beacon_sched` has a reference, `beacon_track`'s only remaining job is the lock counter. A miss clears both, and the re-lock then happens at skip 1 where the EMA is valid again.
  - **`BSCHED_QUANT_US` (1000) is not in the design.** `k_uptime_get_32()` truncates, so the millisecond clock contributes up to ±1 ms of error to the baseline *difference* — 8× the ±0.12 ms arrival jitter the design's §4.2 accounts for. It is absorbed by the baseline length in every real configuration (a tag running at skip K accumulates span K× faster than it takes observations), but it is why a deep skip planned off a *short* baseline widens: 100 observations at skip 1 (span 99) plans 14 ms for a 300-skip, versus 7 ms off a skip-25 baseline. If a deep skip ever has to work off a short baseline, feed the module microseconds instead of milliseconds.
  - **The runner's sleep is interruptible; the CFP slot wait is not.** `uwb_radio_sleep_until()` waits on a `k_sem` and returns `true` if cut short by `uwb_net_runner_wake()` (called from `uwb_set_moving()` and from `tag_alert_raise()`/`_cancel()`). Without it a motion edge or a HELP press would wait out a whole skip — 60 s at IDLE, which for an emergency button is a defect, not a latency figure. A cut-short sleep abandons the skip and forces one full-window re-sync (`force_full_window`, sticky so a give that lands mid-exchange is not lost when the semaphore is drained at the top of the loop). **`uwb_radio_sleep_until_strict()` is used for the CFP slot start and must stay non-interruptible** — waking early there transmits outside the tag's TDMA slot, which is exactly the inter-tag collision `T_SLOT_MS` was sized to prevent.
  - **Out of coverage (`UWB_ST_SCAN`) now sleeps.** `UWB_ACT_SLEEP` is emitted from `SCAN`, where it means "sleep until the next scheduled probe" rather than "until the next superframe"; the interval comes from `scan_backoff_core` (10 s → 30 s → 2 min → 5 min → 15 min → 30 min). A probe is a full superframe (202 ms × 66 mA = 3.7 µAh), so a fixed 5-minute probe would spend 18 % of the whole budget asking "am I home yet?" — hence the deep back-off, and hence motion-gating it: **any activity edge resets to rung 0**, because a tag leaving or entering a building is always in motion. An active HELP pins rung 0. At rung ≥ 2 discovery is suppressed (`run_discovery()` would broadcast and hold a 15 ms window open for anchors that have been absent for two minutes). The ladder sleep is skipped while the radio is not actually asleep, so the first probe after boot — and every probe under `pwr sleep off` — happens immediately.
  - **Re-discovery is wall-clock, not participation-counted.** `REDISCOVER_INTERVAL_MS` (60 s) replaced `REDISCOVER_INTERVAL_SF` (10): counted in participations it would become ~10 minutes at the IDLE tier, staling the anchor pool exactly where the tag moves least.
  - **Tier hysteresis** (`uwb_net_tier_filter()`): promotion to FAST is immediate; FAST → SLOW only `UWB_TIER_HOLD_FAST_MS` (30 s) after the last activity edge, SLOW → IDLE after a further `UWB_TIER_HOLD_SLOW_MS` (60 s) of stillness. Without it a person shifting in a chair flaps the tag into FAST. Called every superframe, not only on an edge — the SLOW → IDLE demotion is a timeout.
  - **Diagnostics:** `pwr sched` / `pwr schedrst`, `pwr scan`, `pwr tier`. `pwr rx` remains the primary way to confirm the RX-on duty cycle actually fell.
  - **If ranging breaks after this change set, revert in THIS order — highest suspicion first.** None of it has been run on hardware, and this firmware has a history of inert-looking changes killing DW3000 RX (see the reverted `dwt_isr()` thread-context work under the `dwt_isr()` entry). Bisect by symptom, not by commit order:
    1. **`CONFIG_PM_DEVICE_RUNTIME=y` (`prj.conf`) + `zephyr,pm-device-runtime-auto` on `&spi3`/`&i2c0` (board DTS).** The riskiest change by a wide margin and the cheapest to undo — four lines. The reasoning that `&spi1` is untouched is that `pm_device_runtime_get()` is a no-op on a device without runtime PM enabled; that is believed, not verified. **Symptom: `P:` stops, or ranging works but `n` collapses. Revert this first, before analysing anything else.**
    2. **`beacon_track` suppression across a skip** (`if (eff_skip <= 1)` in `runner_fn`). Rests on the argument that `bt.tracking && !beacon_sched_have_ref()` is unreachable — a miss clears both, a radio handover resets both — so `beacon_track`'s frozen `period_est` is never used to aim a window. If that is wrong, the runner aims a narrow window off a stale `bt.last_beacon_ms`. **Symptom: repeated `RESCAN miss` starting right after the first successful skip** (not at boot, not immediately — that timing is the tell).
    3. **`UWB_ST_SCAN` now emits `UWB_ACT_SLEEP` unconditionally**, so the radio deep-sleeps on every failed probe. `dw_enter_sleep()`/`dw_wake()` has only ever been exercised at the every-superframe rate; if it is less reliable at a 30-minute duty cycle, an out-of-coverage tag never comes back. **Symptom: tag goes silent out of coverage and does not rejoin when the gateway returns, but recovers on a reset.** Test with `pwr sleep off`, which bypasses the sleep and makes every probe immediate.
    4. **Interruptible `uwb_radio_sleep_until()`.** `uwb_radio_sleep_until_strict()` must remain on the CFP slot wait; if the two were ever transposed the tag would transmit outside its TDMA slot. **Symptom: inter-tag collisions, `n=3` with multiple tags — the exact failure `T_SLOT_MS=24` was sized to prevent**, so it will look like a slot-sizing regression rather than a sleep bug.
    5. **`lease_age()`**. Correct as reasoned and host-tested, but it is the only change that depends on the *gateway's* aging behaviour matching the assumption. **Symptom: `RESCAN seat` (not `RESCAN miss`) at a rate that scales with `listen_skip`.**
    Fastest global bisect: `pwr tier f 1 1` forces `listen_skip = 1`, which makes items 2, 3 and 5 unreachable. If the fault survives that, it is item 1 or item 4.
- **DW3000 ownership:** the runner and the calibration thread share one IRQ line and one `irq_sem` through `wait_event()` (`src/uwb_ss_initiator.c`), which is destructive under concurrency — it opens with `k_sem_reset()` and closes with a global `port_DisableEXT_IRQ()`. It is correct only while exactly one thread drives the radio. `src/uwb_radio_owner.c` enforces that by explicit handover: the runner offers the radio once per superframe at the top of `runner_fn`, leaving it awake and idle; calibration claims it for its whole run. The handover is a mutex (`lock`) plus a condition variable (`cv`) over `enum owner_state { OWNER_IDLE, OWNER_REQUESTED, OWNER_HANDED }`, with every transition made under the mutex. `uwb_radio_yield()` re-checks the claim under the lock and returns without handing over if the claimant withdrew in between — this is what stops the runner being stranded in a `K_FOREVER` wait when a claim times out. `uwb_radio_release()` is a no-op unless a handover is actually outstanding, so a stray release cannot make a later `uwb_radio_yield()` return early and put two threads on the radio. `uwb_radio_request()` fails immediately if a claim is already in flight — single claimant thread at a time is a documented contract, not a guarantee the module enforces by queueing. Known residual: a claimant that dies without calling `uwb_radio_release()` still parks the runner in `K_FOREVER` with no diagnostic. `uwb_radio_yield()` returns `bool` — true only if the radio really changed hands; the runner's reacquire (including `beacon_track_reset()`, worth `BT_WARMUP_N`=8 superframes of full-window RX) runs only then. **PHY-state contract:** that reacquire restores only `dwt_setrxaftertxdelay`, `dwt_setrxtimeout`, `dwt_setpreambledetecttimeout`, `dwt_settxantennadelay`, `dwt_setrxantennadelay`; a claimant that changes anything else (`dwt_configure`, `dwt_configuretxrf`, `dwt_setcallbacks`, frame filtering, PAN/short address) must restore it before releasing or runner RX silently dies. Every `dwt_forcetrxoff()` at a handover point is followed by `dwt_writesysstatuslo(SYS_STATUS_ALL_RX_TO | SYS_STATUS_ALL_RX_ERR)` — an abort can leave RX-error bits set, and the *other* thread's first `wait_event()` would dispatch them as a spurious `EVT_RXERR`. **Any new radio consumer must go through this handover, not add a third caller of `wait_event()`.** A mutex alone would not work — the runner sleeps inside its own loop. Host test: `tests/uwb_radio_owner/` compiles the real module against a pthread shim for `k_mutex`/`k_condvar` (`shim/zephyr/kernel.h`) and runs two threads against it — Zephyr's `native_sim`/`unit_testing` are POSIX-arch boards and do **not** configure on Windows.
- **UWB antenna delay (calibration):** Per-unit, solved on-device and persisted in NVS — see `src/cal.c`/`src/cal_math.c`. Trigger over BLE NUS with `cal <mm>` (reference distance in millimetres). **Calibration deliberately uses the legacy non-addressed exchange** (`do_one_range()`, 10-byte `0xE0` poll / `0xE1` response, no anchor id) — *not* the addressed `do_one_range_anchor()` the positioning sweep uses. This is a bench procedure run against a **stock Qorvo SS-TWR example responder**, which has no concept of an anchor id; switching cal to the addressed frames breaks it against that peer. Do not "unify" the two paths. The cost of the non-addressed poll is real but accepted: `wait_event()` returns on the **first frame of any type**, so foreign traffic in the ~2 ms post-poll RX window costs samples (the gateway beacon is 39 B incl. FCS, over `RX_BUF_LEN`=32, and takes the `cal_n_big` stale-buffer reject path) — calibrate away from a live network. The initiator (`src/uwb_ss_initiator.c`) collects ~100 ranges, rejects outliers (median/MAD), and corrects the combined TX+RX delay toward the reference by a linear step (~2.34 mm per combined unit) over up to 4 iterations until the residual is ≤15 mm, then stores a CRC-checked, PHY-tagged `cal_record` in NVS (DTS `storage_partition`, resolved via devicetree because this NCS Partition Manager build gives all flash to a single `app` region). Other commands: `cal status`, `cal clear`, `cal selftest` (runs `cal_math_selftest()` → `SELFTEST 0` on success), and **`cal last`** — the latched verdict of the most recent run. A run owns the radio for seconds and ends with an NVS write, and the BLE link does not reliably survive that; `ble_log_send()` drops silently with no connection, so a pushed-only verdict is routinely lost and the operator never learns whether the run worked. `cal_verdict()` latches every verdict (and latches `CAL OK` **before** the NVS write). The latch is RAM-only on purpose: `CAL none` after a visible run means the tag *reset* during it, which is otherwise indistinguishable from a dropped link on a device with no console. Pair it with **`rst`** (`tag_reset_reason()`, `src/wdt.c`) — `sreq` means a fatal-error reset, `pwr` means the SoC never reset and the link alone was lost. **NVS is mandatory:** without a valid record for the current PHY the ranging thread reports `CAL REQUIRED` and does not range until a `cal` run succeeds. `TX_ANT_DLY = RX_ANT_DLY = 16371` in `src/phy_config.h` is now only the factory-reference seed/fallback for an uncalibrated unit. Values are PHY-dependent (calibrated for `CONFIG_OPTION_07`: Ch5, PLEN-1024, 850k); `phy_option` in the record invalidates a stored value if the PHY changes. Note: the `CAL loaded`/`CAL REQUIRED` message sent from `main.c` at boot fires before a central connects and is dropped — use `cal status` to read state after connecting. The gate is enforced in the runner via `uwb_net_gate_actions()` (`src/uwb_net.c`), which clears **`UWB_ACT_RUN_SWEEP` only** (`UWB_ACT_RANGING_MASK`) when `cal_is_valid()` is false, while leaving JOIN/KEEPALIVE/DISCOVER/SLEEP intact — an uncalibrated tag keeps its seat and emits no `P:` line. **`UWB_ACT_RUN_DISCOVER` is deliberately excluded**: discovery does no TWR (it broadcasts E2 and collects E4s), so it has no antenna-delay dependence and produces no range to be wrong. Gating it would also pin an uncalibrated tag in `UWB_ST_DISCOVER` forever — the only path to `UWB_ST_RANGING` is `UWB_EV_DISCOVERED`, which the runner emits only inside the gated DISCOVER block — and `UWB_ACT_SLEEP` is emitted from `UWB_ST_RANGING` alone, so `dw_enter_sleep()` would become unreachable and the tag would never deep-sleep the radio (~56 mA back to ~66 mA). That is not just a bench condition: a `phy_option` change invalidates the record for a whole fleet at once. This check lived in `ss_twr_fn` originally and was lost when the runner took over ranging; the documented guarantee was false in between. The gate is applied at two sites in `runner_fn`, not one — once on `uwb_net_handle()`'s return, and again on the GRANT-response re-OR inside the `UWB_ACT_SEND_JOIN` block; the second is defensive (a GRANT currently yields only DISCOVER, which passes the gate anyway), because the re-OR happens after the first gate and any future action it introduced would otherwise bypass it. Contract asserted by `tests/uwb_net/test_uwb_net.c::test_gate_actions()`.

## Calibration Build Image (recommended — NOT yet implemented)

**Calibration should be run from a dedicated build, not from production firmware.** This is the main conclusion of the investigation that closed the `cal` crash but left `cal` itself failing (`CALp 100 1` — 99 of 100 exchanges time out while the peer logs `RESP TX OK`).

Antenna-delay calibration is a **bench procedure**: one tag, one stock Qorvo SS-TWR responder, a known reference distance, a quiet channel. The production image is the opposite of that environment, and it fights the procedure on three fronts:

- **Constant beacon RX.** The runner holds the receiver open for the gateway beacon across most of every 202 ms superframe (and ~100 % of it in `UWB_ST_SCAN`, which is where every `cal` run lands — 3 s off the air exceeds `MISS_MAX`). `wait_event()` returns on the **first frame of any type**, so anything on the air consumes the ~2 ms post-poll RX window that the calibration response needs.
- **DW3000 deep sleep.** `dw_enter_sleep()`/`dw_wake()` cycle the radio between activities, re-running `dwt_restoreconfig()` and re-applying antenna delays and LNA mode underneath a procedure that is trying to hold the PHY constant across ~100 samples.
- **Radio handovers.** Calibration claims the radio through `uwb_radio_owner` for its whole run, so the runner is parked and the tag loses its seat — but the claim/yield/reacquire path is still live machinery running around a measurement that wants nothing else touching the device.

**What the calibration image should do** (sketch — a `cal.conf` overlay plus a small guard in `main.c`):

- Do **not** call `uwb_net_runner_start()`. No beacon RX, no discovery, no sweep, no JOIN/KEEPALIVE — so no competition for the radio and no `uwb_radio_owner` traffic at all.
- Force `dw_sleep_enabled = false` (or omit the sleep path entirely) so the PHY is configured once and stays that way.
- Skip `motion_init()` so tier changes cannot perturb cadence mid-run.
- Keep `ble_log_init()`, `tag_cmd_init()`, `storage_init()` and `uwb_ss_initiator_start()` — the `cal` command, its diagnostics (`CALp`/`CALn`/`CALmm`/`CALx`, `cal last`) and the NVS write all still need to work.
- Keep the watchdog **off** if the image is also meant to be debuggable (see `debug.conf` and the `task_wdt` note there).

The stored `cal_record` is PHY-tagged and lives in NVS, so a unit calibrated with this image carries its values straight over to the production image — provided `CONFIG_OPTION` matches. Verify with `cal status` after reflashing.

2. ~~**`cal` crashes the tag**~~ — **root cause found on hardware with a GDB watchpoint: `samples[got++]` in `run_calibration_locked()` writes past the end of a 128-element array.** `samples[]` is followed in BSS by `cal_n_hdr`, `cal_n_big`, then `int_cb` — motion.c's `gpio_callback`. Index 130 lands exactly on `int_cb.node.next`, so a range measurement in millimetres became the `next` pointer of a live node in gpio0's callback list; every subsequent DW3000 interrupt walked it and took a precise BusFault (`K_ERR_ARM_BUS_PRECISE_DATA_BUS`, `BFAR` = the range value) inside `gpio_fire_callbacks()`, halting the system so the ~120 ms hardware watchdog reset the tag. **The GPIO ISR was the victim, not the cause** — three rounds of fixes aimed at it missed for that reason. Fixed by bounding the write (`got < CAL_MAX_SAMPLES`) plus a `BUILD_ASSERT`. **Still open:** the loop counter register held `0xff7e0000` instead of 0..100 at the moment of the overrun, i.e. `CAL_SAMPLES_PER_ITER` was not actually bounding the loop — something is clobbering a callee-saved register on the sampling path. The bound stops the corruption; the register question is unresolved.
   **How it was found (the method that worked, after several that did not):** `fault`/`rst` narrowed it to a halt+watchdog reset, `addr2line` on the captured PC located the *symptom*, and then `watch int_cb.node.next` in GDB named the *writer* in one shot. When memory is corrupted, go to a data watchpoint early instead of reasoning about who might be at fault.
   **Resolved along the way:** the loop counter register holding `0xff7e0000` was a *consequence* of the overrun, not a separate bug — with the write bounded, `CALp` reports `passes` = exactly 100. **Dead ends, recorded so they are not re-run:** radio-arbitration deadlock (4× timing margin, own `CAL FAIL busy` message); SS-TWR stack overflow (2048→4096 changed nothing; kept anyway for `cal_filtered_mean`'s 1 KB frame); NVS-write radio starvation (`CONFIG_SOC_FLASH_NRF_RADIO_SYNC_MPSL=y`); brownout (`rst` = `dog`); interrupt-stack overflow (`$msp` showed 264 of 2176 bytes used); and **SPI-in-ISR — a real bug, but not this one, and the fix for it had to be reverted for breaking RX** (see the `dwt_isr()` entry under Key Patterns). See the `dwt_isr()` thread-context entry under Key Patterns. Diagnosis chain, for reference: `cal last` → `CAL none` (RAM latch wiped ⇒ reset) → `rst` → `dog` with a sub-2 s return (⇒ a *halt* caught by task_wdt's ~120 ms hardware fallback, not the 10 s channel) → `fault` → `r25` = `K_ERR_ARM_BUS_PRECISE_DATA_BUS`, thread `idle`, PC resolving via `addr2line` into `gpio_fire_callbacks()`. **Awaiting hardware confirmation.** Earlier hypotheses that were investigated and did *not* hold: radio-arbitration deadlock (timing has 4× margin, and it has its own `CAL FAIL busy` message), SS-TWR stack overflow (raising 2048→4096 changed nothing), NVS-write radio starvation (`CONFIG_SOC_FLASH_NRF_RADIO_SYNC_MPSL=y`), and brownout (`rst` = `dog` is a watchdog reset, not a power-on).
   Historical symptom description follows.
   **`cal` completes but the tag drops the NUS link at the end of the run and never reports the verdict.** The peer (a stock Qorvo SS-TWR responder) logs `RESP TX OK` throughout, so the ranging itself works. Leading hypothesis is **stack overflow on the calibration path**: `cal_filtered_mean()` holds 1 KB of locals in a single frame, picolibc is built with `PICOLIBC_DOUBLE_PRINTF_SCANF` so `vsnprintf` is expensive, and every IRQ pushes a 104-byte extended FPU frame onto the thread stack (`-mfpu=fpv4-sp-d16`). `SS_TWR_STACK` was 2048; now 4096. The alternative — the `cal_store()` NVS write starving the radio — is **weakened**: `CONFIG_SOC_FLASH_NRF_RADIO_SYNC_MPSL=y`, so flash operations already run inside MPSL timeslots. Mitigations landed both ways (verdict latched for `cal last`).
   **Confirmed on hardware: the tag takes a fatal error and halts.** `cal last` → `CAL none` (the RAM latch was wiped, so it reset), `cal status` unchanged (it never reaches `cal_store`), `rst` → `dog`, and it returns in under 2 s. Raising `SS_TWR_STACK` to 4096 did **not** fix it, so the fault is not a plain overflow of that thread.
   **Two config facts make this class of bug invisible and must be understood before debugging it:** (1) `CONFIG_RESET_ON_FATAL_ERROR` is **not set**, so a fault does not reboot — `arch_system_halt()` kills interrupts and spins, producing no output at all with `CONFIG_SERIAL=n`/`CONFIG_LOG=n`. (2) `CONFIG_TASK_WDT_HW_FALLBACK=y` with `TASK_WDT_MIN_TIMEOUT=100` + `TASK_WDT_HW_FALLBACK_DELAY=20` arms the **hardware** watchdog at ~**120 ms**, fed from a kernel timer — *not* the 10 s `task_wdt` channel. So a halt is caught in ~120 ms and looks like an instant reboot. `rst` = `dog` + a sub-second return is the signature of a halt, **not** of the 10 s channel expiring.
   **Diagnostics for it:** `fault` reports the K_ERR_* reason, the faulting thread name and the PC from a `__noinit` record that survives the warm reset (`src/wdt.c`); resolve the PC with `arm-zephyr-eabi-addr2line -e build/tag_testting/zephyr/zephyr.elf <pc>`. `stack` reports free-byte high-water marks for the sstwr / runner / bletx threads (needs `CONFIG_INIT_STACKS`). Note `BLE_TX_STACK` is only **512 bytes** for a thread that calls `bt_nus_send()` → `bt_gatt_notify()`, and it drains the burst of diagnostic lines a cal run emits — a live suspect.
   **Hazard found while investigating, not yet proven to fire:** `deca_irq_handler` (`platform/port.c`) runs in **GPIO ISR context** and calls `process_deca_irq()`, which spins `while (port_CheckEXT_IRQ() != 0)`. Any DW3000 status bit that is interrupt-enabled but not cleared by `dwt_isr()` makes that an infinite loop *inside an interrupt* — interrupts blocked, kernel timer starved, hardware watchdog at ~120 ms. `do_one_range()`'s reject paths clear only `RXFCG` and leave other asserted bits set, which is exactly the shape that would trigger it.
   The radio-arbitration layer was investigated and cleared — worst-case runner iteration is ~0.5 s against a 2 s claim, and a claim failure has its own message (`CAL FAIL busy`). Brownout was considered and ruled out: `rst` = `dog` is a watchdog reset, not a power-on.
